## 5. Root cause

1. **Response shape mismatch.** `pro-tier-refresh.js` called `POST https://visa-requirement.p.rapidapi.com/v2/visa/check` (Travel Buddy API on RapidAPI) and read `body.requirement || body.visa_requirement`. The v2 API returns the rule at `body.data.visa_rules.primary_rule.name` (Travel Buddy docs, <https://travel-buddy.ai/api/>). Every successful (HTTP 200) call therefore normalised to `"unknown"`, and the script wrote that over the existing entry with `source: "rapidapi-pro"`.
2. **No guard in this script.** The Feb 2026 fix (f7a6f37, "never overwrite with unknown") went into `update-visa-data.js` and `smart-update.js` but never into `pro-tier-refresh.js`. The commit step also ran `if: always()` with no validation.
3. **Free plan, not Pro.** Exactly 120 pairs were damaged per run, which matches the RapidAPI **free plan (120 requests/month)**. Request 121 got HTTP 429, the script stopped, and the bad results were committed. The workflow is named "Pro tier ($4.99/3,000)", but the key on `RAPIDAPI_KEY` appears to be on the free plan. Check the RapidAPI dashboard (I did not call the API). The weekly `smart-update.js` uses the same key and parser. Its guard skipped the unknowns, so it changed no data, but it may have used up quota.
4. Also from the docs: the API returns HTTP 200 with `"error": true` for bad pairs, demo data marked `is_demo: true` on lower plans, and JSON request bodies. The old script handled none of these.

### Fixes in code
- `scripts/lib/travel-buddy.js`: a strict v2 parser. It returns a result only for a documented shape and a known requirement type. The error flag, quota or auth messages, demo data and unknown shapes are all failures.
- `pro-tier-refresh.js`: never writes unknown or empty results. Failures are logged and skipped, and existing data is untouched. It stops on 401/403/429 or quota errors. Nothing is saved (so no version bump) when nothing changed. A fully failed run exits non-zero. It refuses to start from a missing or corrupt data file. `smart-update.js` uses the same parser.
- `scripts/validate-data.js`: the gate, wired into all 5 workflows before the commit. Run against the real 1 Mar 2026 commit, it fails with "unknown pairs rose from 0 to 120".
- `pro-tier-refresh.yml`: the monthly schedule is commented out (manual `workflow_dispatch` kept), with an explanation.

### Recommendation
- Keep the pro-tier schedule off. If Travel Buddy is kept, run it manually once on a paid plan, read the log (it now prints failure reasons), and check the diff before re-enabling. Its site says the data "must not be used to make official travel, airline boarding, or immigration decisions" and must not be presented as official. Read its API Terms of Use (not shown on the pricing page) on caching and redistribution before storing results in a public repo.
- **Free alternative:** refresh from the Passport Index dataset (`ilyankou/passport-index-dataset`). The repo code is MIT-licensed, but the underlying data comes from passportindex.org, whose own terms govern redistribution. One third-party source says the ilyankou repo is archived, with `imorte/passport-index-data` as the continuation. Check both before relying on them. A monthly job could download the CSV, run `import-free-dataset.js`-style logic that fills only missing or unknown entries, and go through `validate-data.js`. Do not let it overwrite entries that carry `verified`.

## 6. Version-field contract for the app (for the app-fix agent)

`data/version.json` (fetched first) and the top of `data/visa-rules.json` carry the same three fields. `validate-data.js` enforces that they match:

```json
{
  "version": "3.1.0",
  "lastUpdated": "2026-11-05T13:35:39.069Z",
  "dataVersion": 1793885739069
}
```

- **Compare `dataVersion`**: an integer of milliseconds since the Unix epoch (JavaScript `Date.now()`). Update when `remote.dataVersion > storedDataVersion`, as a numeric comparison. It rises whenever the rules change (the gate rejects a rules change without a bump) and never goes down.
- `lastUpdated`: an ISO 8601 UTC string, `new Date(dataVersion).toISOString()`. Use it for display, or as a fallback comparison via `Date.parse()` if `dataVersion` is missing or not a number.
- `version`: a semver label (now **"3.1.0"**, was "3.0.0" since Jan). Do **not** use it for update detection: the automated jobs do not change it. It was bumped to 3.1.0 once, so that already-installed app builds (which compare `version !== stored`) download this repair.
- After a successful download, store `dataVersion` together with the rules (`storage.ts` already has `VisaRulesData.dataVersion`).
